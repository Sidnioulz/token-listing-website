## Why Token Listing?

Design tokens are increasingly prevalent in code environments. Yet, the standardisation efforts of the W3C [Design Tokens Community Group (DTCG)](https://www.designtokens.org/) have focused on the authoring side of things, leaving gaps in interoperability for tools that consume built design tokens in code.

Every tool that handles design tokens in built environments needs its own input format and configuration API. Documentation sites, search engines, differs, changelog generators, linters and MCP servers all need to extend the capabilities of DTCG to understand built design tokens.

Token Listing acts as a shared interchange layer: produced once by compatible design token translators, handling any team's conventions and design token taxonomy, and consumed seamlessly by any compliant tool.

<CardGrid>
  <Card title="Interoperable" icon="puzzle">
    Any compliant translator's output is consumable by any compliant consumer. Switch tools without rewriting your token data pipelines.
  </Card>
  <Card title="Feature Rich" icon="setting">

## How to consume it

<Steps>
1. Validate `meta.version` is an integer your tool knows how to handle.
2. Iterate `data` for token entries, consuming the DTCG fields and `$extensions.listing` fields your tool cares about.
3. Use `meta.modes`, `meta.platforms`, `meta.groups`, and `meta.sourceOfTruth` for top-level context.
</Steps>
